# 科研创新赛道：答辩与演示指南

## 作品定位

题目：**基于证据核查与自适应检索的科研软件开源任务理解与贡献导航方法**

面向的具体问题：科研软件的新手贡献者需要从 Issue 理解任务，再从源码和测试中定位实现入口；仅看 Issue 容易误解，只做静态检索会混入噪声，严格过滤又可能删掉合理推断。

研究贡献放在 A/B/C/D 对照方法和结果分析。可运行门户用来展示任务浏览与新人导读；A/B/C/D 的内部对照通过实验结果文件和 PPT 展示。不要暗示门户本身提供 A/B/C/D 实验控制面板。

## 约三分钟演示顺序

### 1. 先给出任务场景（约20秒）

说明研究软件新手遇到的困难：Issue 描述未必指出具体代码位置，也未必写清验证方法。项目希望把 Issue、源码/测试证据和新人入手步骤连起来。

### 2. 演示新人门户（约60秒）

从项目列表选一个科研软件项目，再打开一个任务，依次展示：

- Issue 的中文导读和要解决的问题；
- 推荐阅读的源码或测试入口及推荐理由；
- 需要的知识基础和建议的开始步骤；
- 相关任务推荐及二者的技术联系；
- 对话入口如何回答针对当前任务的追问。

展示保存的数据与离线页面即可。若切换到 DeepSeek 实时对话，应提前确认网络与 `.env` 配置可用，并准备好失败时的缓存演示。

### 3. 展示方法和消融（约60秒）

用一张流程图讲 D 组：Issue 与固定源码快照构建证据包，模型生成结论，逐条核查；证据不足则按缺口补检并重做分析，最多两轮。

随后讲 A/B/C/D 的差别。强调证据核查与自适应补检是两个独立设计因素，不把“检索到了材料”直接等同于“结论正确”。

### 4. 展示结果和边界（约40秒）

当前39个留出任务的156份答案已经完成 DeepSeek Pro 模型辅助评分。D 组在四项模型评分中的均分最高；C 组的得分低于 B 组，适合作为“核查过严会损害回答质量”的分析案例。

明确说明这是单个模型裁判的0—4等级评价，不是人工金标准，也不是实际准确率。能力门槛专项评审尚未覆盖全样本，不展示它的全量结论。

## PPT建议：6页

1. **问题与对象**：科研软件新手为什么难以从 Issue 找到源码入口和验证方式。
2. **研究问题**：源码证据、逐条核查和自适应补检各自带来什么变化。
3. **方法流程**：证据包、分析、核查、按缺口补检、停止条件。
4. **实验工作量与设计**：先展示五项目967条Issue记录（945个具体任务、22份指引），再明确正式留出集是39个独立Issue；每题跑A/B/C/D四组，合计156份分析答案。说明最初一个试点和五个调试样本已排除，避免把156份答案说成156个不同Issue。
5. **结果和失败分析**：展示模型评分表；重点解释 C 组为什么低于 B、D 组在哪些指标改善。
6. **可运行演示与应用价值**：现场操作路径、适用对象、局限和下一步计划。

## 提交前检查

- 代码仓库或可运行 Demo 链接、PPT，以及清晰的安装启动步骤。
- Demo 不依赖现场模型服务才能展示主要界面；准备本地缓存作为备选。
- 报告和PPT中把 DeepSeek Pro 评分标成“模型辅助评价”，不要称为准确率、人工验证或显著提升。
- 核实 `39/39` 个任务和 `156/156` 条主评审记录；保存 `holdout_manifest.json` 和 `model_evaluation.md`。
- 能力门槛专项评审如未完成39项，不纳入全样本统计。
- `.env` 中的 API 密钥不得放进公开仓库、压缩包、截图或演示录屏；提供空白 `.env.example` 即可。
